**2026년 11월 19일(목, 한국) | Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems | HE-01 | 핵심 질문: Agent Harness, Evaluation Harness, Orchestrator를 왜 같은 계층으로 설계하면 안 되는가?**

HE-01의 실제 독서 완료가 확인되지 않아 같은 차시를 유지합니다. 오늘은 이미 읽은 §2.2의 정의를 **'행동을 실행하는 주체 / 행동을 시험하는 주체 / 여러 실행체를 조율하는 주체'** 세 가지 책임으로 다시 구분합니다. RAG-01 완료 기록은 보존하고 RAG-02는 미완료·보류 상태로 유지합니다. 오늘도 누적 과제 없이 30분입니다.

## 1. 3분 복습 | 하나의 Agent를 누가 실행하고 누가 평가할까?

**회상 질문 하나:** 코드 수정 Agent가 파일을 수정하고 테스트를 실행했습니다. 이 Agent가 정답을 냈는지 판단하는 프로그램과 실제 파일을 수정한 프로그램은 같은 실행 주체라고 볼 수 있을까요?

가능하면 종이에 **모델 → 실행 시스템 → 평가 시스템**이라는 세 칸을 그리고, 각각 하나의 역할을 적으세요. 어떤 프로그램이 다른 프로그램을 감싸는지 예측하는 것이 오늘의 출발점입니다.

## 2. 20분 원문 읽기 | §2.2의 마지막 두 경계 사례

**고정 원문:** [arXiv PDF v1](https://arxiv.org/pdf/2609.00006v1) · [논문 등록·버전 이력](https://arxiv.org/abs/2609.00006).

**버전:** arXiv:2609.00006v1, 최초 등록 2026년 7월 15일. 이번에 읽는 원문과 구분되는 별도 arXiv 수정본은 확인하지 않았습니다.

**읽을 위치:** **PDF 3쪽 §2.1 “Definition and Genealogy”의 첫 정의**, **PDF 4쪽 §2.2 “What a Harness Is Not”의 마지막 두 항목** (*evaluation harness*, *orchestrator*). 원문 3~4쪽의 텍스트와 페이지 이미지를 확인했습니다. PDF 4쪽 하단 Figure 1은 보이지만 시각적 세부 해석은 다음 차시 HE-02로 남겨둡니다.

**① 4분 — PDF 3쪽 §2.1: '누가 모델을 행동하게 만드는가?' 재확인.**

저자의 **Agent = Model + Harness** 정의를 다시 읽습니다. 여기서 harness는 모델에 붙어 실제 저장소·도구와 상호작용하게 하는 실행 런타임입니다. 정의에서 *loop*, *tools*, *safety controls*를 찾아 표시하세요.

**관찰할 것:** LLM이 “파일 수정”이라는 도구 사용을 제안할 때, 모델의 출력이 어떻게 실제 동작으로 이어질지 담당하는 영역은 모델인가, 하네스인가?

**② 9분 — PDF 4쪽 §2.2 세 번째 항목: Evaluation Harness.**

첫 번째 핵심 개념 **Evaluation harness(평가 하네스)**는 **이미 구성된 Agent를 시험 과제에 연결하고 동작·결과를 평가하는 실행 환경**입니다. 반면 agent harness는 **모델을 감싸서 행동 가능하게 만드는 실행 환경**입니다. 저자가 SWE-bench를 예로 들며 두 종류의 *wrapping* 방향을 구분하는 문장을 찾으세요.

원문을 보며 아래 문장의 주어와 목적어를 직접 적어봅니다.

- Agent harness는 ______을 감싸 ______하게 한다.
- Evaluation harness는 ______를 감싸 ______를 수행하게 한다.

**관찰할 것:** 코딩 Agent가 테스트 명령을 직접 실행한다면, 그 테스트 명령 자체가 곧바로 이 논문에서 말하는 *evaluation harness*가 되는지 검토하세요. 'Agent가 자기 작업을 검증하는 단계'와 '외부에서 Agent 전체를 벤치마크하는 체계'를 구분하는 것이 핵심입니다.

**③ 7분 — PDF 4쪽 §2.2 네 번째 항목: Orchestrator.**

두 번째 핵심 개념 **Orchestrator(오케스트레이터)**는 **하나 또는 여러 하네스의 실행을 상위에서 조율하는 구성요소**입니다. 저자는 오케스트레이터가 자체 코드 편집 루프를 갖지 않는다는 점을 구분 기준으로 삼으며, Omnigent를 대조 사례로 제시합니다.

아래 **가상의 기업 Agent 실행 사례**를 원문의 두 항목과 연결해 분류하세요. 논문에서 효과를 실험한 사례가 아닙니다.

| 가상 상황 | 어디에서 책임을 찾을까? |
|---|---|
| 계약서 조회 Agent가 파일을 읽고 조건을 추출 | 모델을 실제로 작동시키는 하네스 |
| 50개 계약서로 Agent의 정답 여부를 반복 검사 | Agent를 감싸 시험하는 평가 하네스 |
| 조회 Agent와 계약 검토 Agent를 순서대로 호출 | 여러 실행체를 조율하는 오케스트레이터 |

**관찰할 것:** 하네스에 여러 sub-agent를 호출하는 기능이 있을 수 있는데도 왜 별도의 *meta-harness / orchestrator*라는 용어가 필요한지, §2.2가 채택한 '자체 편집 루프' 기준으로 설명해 보세요. 제품 이름을 암기할 필요는 없습니다.

**저자 주장과 한계의 구분:** 이 절은 분석 대상의 **구조적 경계**를 정의합니다. 기업 업무에서 평가 하네스를 분리하면 성공률이 몇 퍼센트 오른다는 실험은 제시하지 않습니다. 위 계약서 예시는 독해를 위한 아키텍처 적용 연습입니다.
