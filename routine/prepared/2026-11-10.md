**2026년 11월 10일(화, 한국) | Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks | RAG-02 | 핵심 질문: 검색기(DPR)와 생성기(BART)는 각각 어떤 역할을 맡고, 두 모델의 입출력은 어떻게 연결되는가?**

RAG-01은 사용자가 명시적으로 완료를 확인했습니다. 이전 차시에서 확인한 '파라미터 지식과 외부 검색 지식을 결합하되, 답변의 정확성이 자동 보장되지는 않는다'는 이해에서 출발해 **검색기와 생성기의 책임을 분리**해 봅니다. RAG-02는 아직 읽기 완료로 처리하지 않았습니다.

## 1. 3분 복습 | 검색된 지식과 모델의 역할

**회상 질문 한 가지:** RAG-01에서 모델의 *parametric memory*와 외부 *non-parametric memory*를 조합한다고 했습니다. 만약 질문에 대한 최신 문서가 외부 인덱스에 들어 있다면, **검색기가 책임질 일과 생성기가 책임질 일**을 어떻게 구분할 수 있을까요?

정답을 미리 확정하지 말고 두 구성 요소의 입력과 출력을 각각 예상해 적어보세요.

## 2. 20분 원문 읽기 | Figure 1 → DPR → BART

**고정 원문:** [RAG 논문 PDF v4](https://arxiv.org/pdf/2005.11401v4) · [arXiv 발표·수정 이력](https://arxiv.org/abs/2005.11401). 최초 공개는 **2020년 5월 22일(v1)**, 오늘 읽는 **v4는 2021년 4월 12일 수정본**입니다. 범위는 **인쇄본/PDF 2쪽 Figure 1과 3쪽 §2.2 “Retriever: DPR”, §2.3 “Generator: BART”**입니다.

**① 5분 — PDF 2쪽 Figure 1: 화살표의 입출력을 표시하기.** 사용자 입력 `x`가 **Query Encoder → MIPS → Document Index**를 거쳐 후보 문서 `z₁…zₖ`로 연결되는 길을 찾으세요. 다음으로 문서 후보들과 입력이 Generator에 전달되는 길을 찾습니다. 종이에 **(a) 검색기의 출력**, **(b) 생성기의 출력**을 서로 다른 말로 적어보세요. Figure 1의 *Marginalize*는 여러 문서에 대한 예측 확률의 결합이며, 문서 내용을 진위 판정하는 별도 모듈이 아닙니다.

**② 9분 — PDF 3쪽 §2.2 Retriever: DPR: 검색 점수의 의미 이해하기.** 논문은 DPR의 **bi-encoder** 구조를 사용합니다.

오늘의 개념 **① Bi-Encoder(쌍 인코더)**: 질문과 문서를 **각각의 인코더**로 벡터화한 다음, 두 벡터가 얼마나 잘 맞는지 점수로 비교하는 구조입니다. 논문의 표기에서 `q(x) = BERTq(x)`는 질문 벡터이고, `d(z) = BERTd(z)`는 문서 벡터입니다. 다음 관계를 원문에서 찾으세요.

`pη(z|x) ∝ exp(d(z)ᵀ q(x))`

이 식은 **어떤 문서를 가져올지 점수화**하기 위해 등장합니다. `x`는 질문, `z`는 후보 문서, `d(z)ᵀq(x)`는 두 벡터의 내적이며, `pη(z|x)`는 질문에 조건화된 검색 분포입니다. 점수가 높은 상위 `K`개 문서를 찾는 과정이 **MIPS(Maximum Inner Product Search)**입니다. 지수함수의 세부 계산보다는 '질문 → 문서 점수 → top-K 문서'가 되는 이유를 설명할 수 있으면 충분합니다.

**원문 관찰:** DPR은 질문과 문서를 **하나의 결합 텍스트로 인코딩**할까요, **별도의 두 벡터로 변환**할까요? §2.2 끝에서 논문이 어떤 사전학습 검색기를 초기값으로 사용했는지도 확인하세요.

**③ 6분 — PDF 3쪽 §2.3 Generator: BART: 검색 결과를 어떻게 답변에 쓰는가?**

오늘의 개념 **② Encoder–Decoder(인코더–디코더)**: 입력을 인코더가 표현으로 바꾸고, 디코더가 그 정보를 조건으로 출력 토큰을 차례로 생성하는 방식입니다. 저자들은 **BART-large(4억 파라미터)**를 생성기로 사용하고, **원래 입력 `x`와 검색 문서 `z`를 이어 붙여(concatenate)** BART에 제공합니다. 논문에서 생성기는 `pθ(yᵢ | x, z, y₁:ᵢ₋₁)`로 표현됩니다.

표기를 데이터 흐름으로 해석해 보세요. `yᵢ`는 **지금 생성할 토큰**, `y₁:ᵢ₋₁`는 **앞서 생성한 토큰들**입니다. 즉, 생성기는 **질문 + 검색 문서 + 지금까지 쓴 내용**을 보고 다음 토큰을 예측합니다.

**원문 관찰:** §2.3에서 모델이 질문과 문서를 결합하는 구체적인 방법을 한 문장으로 표시하세요. 검색기가 출력한 **문서 후보**와 생성기가 출력하는 **토큰 시퀀스**를 구분해 보세요.

**정확성 경계:** 논문이 제안한 검색·생성 분업은 근거 문서에 대한 자동 사실 검증을 보장하지 않습니다. 또한 이 논문의 구현에서 어떤 인코더를 학습 중 고정했는지는 다음 쪽의 §2.4 Training을 별도로 읽어야 정확하게 판단할 수 있습니다. 오늘은 구조 이해에 집중합니다. [원문 PDF v4](https://arxiv.org/pdf/2005.11401v4)

## 3. 5분 이해 기록 | 각 구성 요소의 책임을 설명하기

| **근거가 있는 원문 위치** | Figure 1 또는 §2.2/§2.3에서 찾아낸 **특정 문장·식·그림 부분** |

**자기 점검 1:** `q(x)`와 `d(z)`는 각각 무엇을 나타내며, MIPS가 반환하는 것은 문서인가 답변인가요?

**자기 점검 2:** BART가 새로운 답변을 만들 때 검색 결과 `z`뿐 아니라 `x`도 필요한 이유를 어떻게 설명하겠습니까?

오늘의 목표는 논문의 수식이나 모델 파라미터 수를 외우는 것이 아니라, **'검색 점수'와 '토큰 생성 확률'이 서로 다른 결과**라는 점을 설명하는 것입니다.

## 4. 2분 다음 단계 | Agent 아키텍처에 연결하기

**가상 업무 사례:** 에이전트가 거래처의 최근 변경 계약서를 검색해 결제 조건을 설명한다고 가정합니다. 검색 단계에서는 **변경 계약서가 top-K에 포함되는가**, 생성 단계에서는 **해당 계약서에 적힌 조건을 왜곡 없이 설명하는가**를 서로 다른 성공 기준으로 평가할 수 있습니다. 이는 논문에서 특정 기업 시스템을 평가한 결과가 아니라 실무 설계 제안입니다.

**적용 질문 한 가지:** 거래 조건 Agent의 오류를 추적하려면, 검색 단계와 생성 단계에서 각각 **어떤 입력·출력·평가 항목**을 로그로 남겨야 할까요?
