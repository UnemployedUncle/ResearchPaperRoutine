**2026년 11월 17일(화, 한국) | Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems | HE-01 | 핵심 질문: “모델에게 하지 말라”고 지시하는 것과, 실제 실행을 통제하는 것은 아키텍처상 어떻게 다른가?**

HE-01 독서 완료가 확인되지 않아 같은 차시를 유지합니다. 오늘은 이미 다룬 용어 목록을 반복하지 않고 **모델의 제안, 실행 가능한 도구, 실행 시점의 권한**을 구분하는 데 집중합니다. 기존 RAG-01 완료는 보존되었으며 RAG-02는 미완료·보류입니다.

## 1. 3분 복습 | 모델의 판단과 프로그램의 행동

**회상 질문 하나:** 코딩 Agent가 “파일을 삭제한 뒤 다시 만들겠습니다”라고 답변했습니다. 모델이 이렇게 말한 사실만으로 파일이 실제 삭제되었다고 판단할 수 있을까요?

예상 답변에 **도구 호출, 실행 승인, 실행 결과** 중 어떤 정보가 추가로 필요한지 떠올려 보세요.

## 2. 20분 원문 읽기 | 모델 밖의 실행 책임 찾기

**고정 원문:** [arXiv PDF v1](https://arxiv.org/pdf/2609.00006v1) · [arXiv 제출 이력](https://arxiv.org/abs/2609.00006). 최초 등록은 **2026년 7월 15일**, 읽는 버전은 **arXiv:2609.00006v1(2026년)**입니다. 별도의 수정본을 읽는 것으로 간주하지 않습니다.

**확인한 원문 범위:** **PDF 3쪽(인쇄 3쪽) §2.1 “Definition and Genealogy”의 정의 문장과 §2.2의 도입부**, **PDF 4쪽(인쇄 4쪽) §2.2 “What a Harness Is Not”의 네 항목**. 오늘은 이 두 쪽만 읽습니다. 2026년 11월 17일 원문 PDF 텍스트와 두 페이지 이미지를 직접 확인했습니다. §2.3의 Figure 1은 다음 차시 범위이므로 오늘 해석하지 않습니다.

**① 4분 — 3쪽 §2.1: “모델 밖”은 어디까지인가?**

§2.1 첫 단락에서 **Agent = Model + Harness**와 하네스의 범위를 정의하는 대목을 찾아 표시하세요. 저자들은 loop, tools, context, safety controls, orchestration, extension surfaces를 모델을 외부 세계에 연결하는 런타임의 요소로 제시합니다.

오늘의 첫 개념 **Runtime(실행 환경)**은 설계 문서나 프롬프트 자체가 아니라, 실제로 모델의 출력을 받아 프로그램 동작으로 이어 주는 계층입니다.

**관찰 질문:** 모델이 ‘이 파일을 열겠다’고 *제안*하는 순간과, 프로그램이 파일 열기 작업을 *실행*하는 순간 사이에는 무엇이 더 필요할까요? §2.1의 정의 중 이 간극을 설명하는 표현을 찾아보세요.

**② 9분 — 4쪽 §2.2: 구조 코드와 실제 실행 시스템 구분하기**

§2.2의 첫 두 항목을 비교합니다. 저자는 **scaffold**를 루프와 등록부 등 *구조적 코드*, **harness**를 그러한 구조를 포함해 배포된 *런타임 산출물*로 구분할 때가 있다고 설명합니다. 이어 **agentic framework**는 개발자가 가져다 쓰는 라이브러리인 반면, harness는 개발자가 그 안에서 작업하는 런타임이라고 대비합니다.

원문에서 **Mini-SWE-Agent의 간결한 scaffold**와 **Claude Code의 권한 시스템·플러그인 환경**이 예로 제시되는 지점을 확인하세요. 여기서 복잡한 시스템이 성능상 더 낫다고 판단하지 마세요.

오늘의 두 번째 개념 **Evaluation harness(평가 하네스)**는 Agent 자체를 과제에 연결해 결과를 시험하는 실행 환경입니다. §2.2에서는 **Agent harness가 모델을 감싸 행동하게 하는 것**과 **Evaluation harness가 Agent를 감싸 시험하는 것**의 방향이 다르다고 설명합니다.

다음 두 문장을 원문에 근거해 구분해 보세요.

| 질문 | 표시할 대목 |
|---|---|
| “모델이 행동할 수 있게 만든다”는 어느 harness인가? | §2.2 evaluation harness 구분 |
| “행동한 Agent의 결과를 시험한다”는 어느 harness인가? | §2.2 evaluation harness 구분 |

**③ 7분 — 4쪽 §2.2의 경계를 가상 승인 사례에 적용하기**

아래는 **논문이 실험한 사례가 아니라 실무 설계 연습**입니다. 계약 메일 Agent가 외부 메일 발송을 제안한다고 가정합니다.

| 상황 | 내가 확인할 경계 |
|---|---|
| 프롬프트에는 “승인 후 발송”이라고 써 있다 | 이 문장만으로 실제 발송이 차단되는가? |
| 메일 발송 도구가 등록되어 있다 | 모델이 제안한 호출을 실행하는 곳은 어디인가? |
| 승인 정보가 없는데 발송을 시도한다 | 허용 여부를 판정하고 차단하는 책임은 어디에 두는 것이 좋은가? |
| 테스트에서 미승인 발송을 시도한다 | 그 차단 동작을 재현하고 판정하는 곳은 어디인가? |

§2.2에서 **scaffold / harness / evaluation harness / orchestrator**의 각 정의로 돌아가 위 상황을 분류하세요. 특히 orchestrator가 상위에서 여러 harness를 조율하지만 자체 편집 루프는 수행하지 않는다는 원문의 경계도 확인합니다.

**근거의 한계:** 이 논문은 하네스의 소스 코드 구조를 비교합니다. “승인 검사를 실행 코드에 두자”는 오늘의 실무 설계 제안이지, 해당 계약 메일 시나리오를 논문이 실험했다는 뜻은 아닙니다. 특정 구조의 성공률 우위도 이 대목에서 입증하지 않습니다.
