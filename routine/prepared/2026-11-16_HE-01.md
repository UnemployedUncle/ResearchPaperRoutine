## 2. 20분 원문 읽기 | Harness의 경계 네 가지

**고정 원문:** [arXiv PDF v1](https://arxiv.org/pdf/2609.00006v1) · [arXiv 원문 등록 정보](https://arxiv.org/abs/2609.00006). 읽기 판본은 **arXiv:2609.00006v1**입니다. 최초 등록 정보에는 **2026년 7월 15일**이 표시되어 있으며, 확인되지 않은 후속 수정본 연도는 쓰지 않습니다.

**범위:** **§2.1 “Definition and Genealogy” 마지막 정의 부분 → §2.2 “What a Harness Is Not” 전체**. 원문 텍스트와 절 제목은 확인했지만 PDF 페이지 이미지 호출이 실패했으므로, 확인하지 않은 페이지 번호·그림·표의 시각적 설명은 사용하지 않습니다.

**① 4분 — §2.1: Agent = Model + Harness를 다시 읽기.** 저자가 하네스를 언어모델과 외부 세계를 연결하는 런타임으로 정의한 문장을 찾으세요. 프롬프트, 모델 가중치, 도구 등록·실행, 권한 제어 가운데 **모델 바깥에서 수행되는 것**에 표시하세요.

**② 10분 — §2.2: 네 가지 “not”의 대비 구조 읽기.** 저자는 하네스를 (a) scaffold, (b) agentic framework, (c) evaluation harness, (d) orchestrator와 구분합니다. 단어별 정의를 외우기보다 **누구를 감싸고, 무엇을 실행하며, 누가 사용하느냐**를 기준으로 문장마다 표시하세요.

오늘의 핵심 개념은 두 가지입니다.

- **Scaffold(스캐폴드)**: 루프·도구 등록부처럼 Agent를 구성하는 **구조적 코드 뼈대**입니다. 논문은 실제 배포되어 작동하는 하네스와 실용적으로 겹치지만, 구분이 필요한 경우 구조 코드와 런타임 산출물을 나눕니다.
- **Evaluation harness(평가 하네스)**: 모델을 행동 가능한 Agent로 만드는 실행 시스템이 아니라, **이미 구성된 Agent를 테스트 과제에 연결하고 평가**하는 시스템입니다. “하네스”라는 단어는 같지만 감싸는 대상이 다릅니다.

§2.2에서 나머지 두 경계도 직접 확인하세요. Framework는 개발자가 불러와 사용하는 라이브러리인지, Harness는 그 안에서 일하는 실행 환경인지 구분하고, Orchestrator는 하나 이상의 하네스를 조율하면서 자체 편집 루프를 갖는지 아닌지 확인합니다.

다음 빈칸을 채워 보세요.

| 비교 | 원문에서 확인할 핵심 차이 |
|---|---|
| Scaffold ↔ Harness | 코드 ______ ↔ 실제 ______ |
| Framework ↔ Harness | 개발자가 ______하는 라이브러리 ↔ 개발자가 ______에서 일하는 런타임 |
| Evaluation harness ↔ Agent harness | ______를 감싸 평가 ↔ ______을 감싸 행동하게 함 |
| Orchestrator ↔ Harness | 여러 실행체를 ______ ↔ 자체 ______을 수행 |

**③ 6분 — §2.2의 차이를 가상 Agent에 적용하기.** 아래 사례는 **논문의 실험이 아닌 업무 설계 연습**입니다. 계약서 비교 Agent를 구축하면서 LangGraph 등의 라이브러리를 활용하고, 실행 루프와 조회 도구를 배포하고, 별도의 테스트 프로그램이 정답 계약 조건을 비교하고, 상위 관리자가 여러 Agent를 호출한다고 가정합니다.

원문에 근거해 네 요소를 각각 *framework / agent harness / evaluation harness / orchestrator*로 분류하세요. 특히 **평가 프로그램이 계약서를 직접 수정하는 Agent라고 할 수 있는가?**를 따져보세요.

저자의 주장은 *아키텍처 구분*입니다. 이 연구는 11개 하네스의 소스 구조를 비교했으며, 이 네 요소를 구분하는 것만으로 작업 성공률이 높아진다는 실험 결과를 제공한 것은 아닙니다.
