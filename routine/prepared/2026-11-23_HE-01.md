**2026년 11월 23일(월, 한국) | Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems | HE-01 | 핵심 질문: 같은 LLM의 도구 사용 제안이 왜 실행 환경에 따라 다른 실제 행동으로 이어지는가?**

현재 확인된 진도에는 **HE-01 독서 완료 응답이 없어** 차시를 유지합니다. 오늘은 용어를 다시 나열하는 대신, **모델의 제안 → 프로그램의 실행 판단 → 실제 행동**을 원문 정의와 대조해 정리합니다. 과거 RAG-01은 완료, RAG-02는 미완료·보류입니다.

## 1. 3분 복습 | '도구 호출하겠다'는 말과 실제 실행

**회상 질문 하나:** LLM이 “고객 계약서를 읽고 가격을 확인하겠습니다”라고 응답했습니다. 하지만 시스템에는 파일 접근 권한도, 계약서 조회 도구도 연결되어 있지 않습니다. 이 상태에서 모델의 능력과 Harness의 책임을 어떻게 구분하겠습니까?

먼저 **모델이 제안한 행동**과 **프로그램이 허용·실행한 행동**을 두 문장으로 나누어 떠올리세요.

## 2. 20분 원문 읽기 | 정의를 실행 책임으로 바꾸기

**읽을 원문:** [고정 arXiv PDF v1](https://arxiv.org/pdf/2609.00006v1) · [arXiv 등록 및 판본 이력](https://arxiv.org/abs/2609.00006).

**버전과 위치:** arXiv:2609.00006v1은 **2026년 7월 15일 제출**되었습니다. 본문은 2026년 4월의 이전 연구 판본을 언급하지만, 오늘 읽는 arXiv v1과 구별합니다. **PDF 3쪽 §2.1 “Definition and Genealogy”, PDF 4쪽 §2.2 “What a Harness Is Not”**을 읽으세요. 두 페이지의 본문과 페이지 이미지를 확인했습니다. §2.3과 Figure 1은 다음 차시로 남깁니다.

**① 6분 — 3쪽 §2.1: 저자가 채택한 정의에서 '행동' 찾기**

§2.1 첫 정의의 **Agent = Model + Harness**를 확인하세요. 바로 뒤에서 저자가 *model*과 *harness*에 각각 어떤 책임을 할당하는지 밑줄을 긋습니다. 이어 Macedo의 정의를 채택한다고 밝히는 문장에서 “모델을 감싸 저장소에 행동하게 하는 계층”의 의미를 찾아보세요.

**핵심 개념 1 — Runtime(런타임):** 프로그램이 실제 동작하는 실행 환경입니다. 논문의 Harness는 단순한 프롬프트가 아니라 모델을 도구·컨텍스트·안전 통제 등과 연결하는 런타임을 가리킵니다.

**원문 관찰:** 모델이 파일 수정을 *제안*했을 때, 그 제안을 허용하고 실행·거절하는 기능은 정의상 모델 자체인가, 모델 바깥의 계층인가? 이 질문을 텍스트에 근거해 답하세요.

**② 8분 — 4쪽 §2.2 앞의 두 경계: 설계된 코드와 실제 실행체**

첫 번째 항목 “A harness is not a scaffold—quite”를 읽고, 저자들이 **구조를 나타내는 코드**와 **실제로 제공되는 실행 산출물**을 어떤 말로 구별하는지 찾으세요. Mini-SWE-Agent와 Claude Code를 *기능 규모가 다른 예시*로 제시한 부분에 표시하세요.

**핵심 개념 2 — Scaffold(스캐폴드):** 반복 루프·도구 등록부 등 구현 구조를 이루는 코드의 뼈대입니다. 저자는 현장에서 scaffold와 harness를 거의 동의어로 쓰기도 하지만, 구분할 때 Harness를 실제 배포되는 런타임으로 설명합니다.

다음 “A harness is not an agentic framework” 항목을 이어 읽습니다. 프레임워크를 **개발자가 가져다 쓰는 라이브러리**, 하네스를 **개발자가 그 안에서 일하는 실행 환경**으로 구분하는 이유를 생각하세요.

**원문 관찰:** 프레임워크로 Agent 프로그램을 만들 수 있다는 사실과, 이를 실제로 운영 가능한 Harness로 제공했다는 사실은 왜 다른가요? 논문도 이 경계가 2026년에 흐려지고 있다고 하므로 *두 개념이 완전히 배타적*이라고 답하지 마세요.

**③ 6분 — 4쪽 §2.2 뒤의 두 경계: 실행과 평가의 책임**

Evaluation harness와 orchestrator 항목을 읽고, 아래 표 오른쪽에 원문의 구분 기준을 짧게 적으세요. 왼쪽은 이해를 돕기 위한 가상 사례이며 논문이 실험한 사례가 아닙니다.

| 가상 상황 | 해당 책임을 맡는 계층을 원문 기준으로 판단 |
|---|---|
| LLM의 도구 호출을 실제 파일 조회로 연결한다 | ______ |
| 완성된 Agent를 정해진 테스트 과제에서 평가한다 | ______ |
| 복수의 Agent 실행체를 상위에서 조정한다 | ______ |

저자는 평가용 Harness가 **Agent를 감싸 시험**하고, Agent Harness는 **Model을 감싸 행동**하게 한다고 대비합니다. 또 상위 조율 계층은 자체 코드 편집 루프가 없다는 점으로 구분합니다.

**오늘의 증거 범위:** 위 내용은 논문의 구조적 정의입니다. 정의만으로 특정 기업용 Agent가 더 정확하거나 안전하다는 성능·보안 실험 결과를 주장할 수 없습니다.
